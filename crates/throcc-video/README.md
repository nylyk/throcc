# throcc-video

The video codecs and the pictures between them: one `Encoder` and one `Decoder` with a backend per platform, and the NV12 frames they take and give. It knows codecs and frames, nothing of sessions, keys or the wire beyond `Codec`. `throcc-client-core` always depends on it; the server never does, which `check-server-deps.sh` enforces.

A build with no backend still has both types. They never open: `Encoder::open` fails with `NoEncoder` and `Decoder::new` with `NoDecoder`, so the client does voice only without a `cfg` of its own. `ENCODES` says whether a build can share at all.

| Module | Holds |
| --- | --- |
| `lib.rs` | `Frame` as the renderer gets it, the encoder's config and its access units, `MaxSize`, the errors, `ENCODES`, and which frames in GPU memory an encoder refuses after one fails |
| `output.rs` | `Output`: where a decoder shows its pictures itself on the phones. The app hands over a `View` (an Android `Surface`'s window, an iOS `AVSampleBufferDisplayLayer`) at any time, before or while the share is watched, and takes it away again; the decoder follows. Desktops draw the pictures the decoder hands out and leave it empty |
| `frame.rs` | NV12 pictures in memory: test patterns, shrinking, conversion from 4-byte RGB and to BGRA, copying planes with strides, and the sizes a share is fitted to, filling the frame where only rounding separates the shapes |
| `dmabuf.rs` | Linux: a captured picture still in GPU memory, as DRM PRIME planes, with the crop that holds what is shared where the producer marked one |
| `nal.rs` | Apple and tests: H.264 and HEVC access units between Annex B, as senders send them with the parameter sets before each keyframe, and VideoToolbox's 4-byte length-prefixed NAL units with the parameter sets in a format description |
| `switches.rs` | Switches for testing, read once from the environment: `THROCC_SOFTWARE_DECODE` decodes in software where there is a software decoder of ours (dav1d and libvpx on the phones and Macs, FFmpeg's on Linux and Windows), `THROCC_CODEC` limits encoders to one codec |
| `software/` | dav1d for AV1 (`dav1d.rs`), with frame threads whose pictures `drain` brings out once units stop, and libvpx for VP9 (`vpx.rs`), which also encodes VP9 on macOS. `mod.rs` holds the software decoder Apple and Android fall back to, and the I420 and NV12 conversions. Linked statically on Apple and Android (built by `packaging/codecs/build.sh`), and from the system's anywhere with the `software` feature, for their tests |
| `apple/` | macOS and iOS, whatever the features. `decode.rs`: VideoToolbox decodes H.264 and HEVC into full-range NV12 pixel buffers renderers draw uncopied (`pixel_buffer.rs`), falling back to Apple's own software decoders where the hardware lacks them, and AV1 too where the hardware decodes it, with a format description built from the sequence header (`av1.rs`); other AV1, and VP9, decode in dav1d and libvpx, into pixel buffers too. `encode.rs`: hardware HEVC, then H.264, from captured pixel buffers, flushing each frame before the next and opening a new session when the system invalidates one, as iOS does when the app leaves the screen, and on macOS VP9 in libvpx where there is no hardware encoder. Pictures of another size are scaled into the encoder's on the GPU with black bars (`transfer.rs`, which also pools pixel buffers and turns sideways pictures upright for iOS captures). `attributes.rs` builds the CoreFoundation dictionaries sessions and buffers are configured with. On iOS each picture due goes into the app's display layer (`view.rs`), shown at once. `tests.rs` round-trips through Apple's software encoders |
| `android/` | `encode.rs`: MediaCodec encodes HEVC, then H.264, from its input surface, which the app draws the screen into; the share thread drains its units, the parameter sets put before every keyframe, and the codec sends the last picture again while the screen stands still. `decode.rs`: MediaCodec decodes straight into the app's surface, hardware first, from the next keyframe whenever the surface changes and it can't move to the new one; AV1 and VP9 that MediaCodec can't take, or that keep failing in it, decode in dav1d or libvpx. `codec.rs`: the MediaCodec itself, where a decoded picture stays as a `CodecFrame` until shown or dropped, at most three out at once, so pictures held back for the share audio can't starve it. `window.rs`: the surface's `ANativeWindow` as the `View`, which software pictures are copied into as YV12 |
| `ffmpeg/` | Linux and Windows with the `ffmpeg` feature. `encode.rs`: hardware AV1, HEVC and H.264 through NVENC, Media Foundation and VA-API, then VP9 in libvpx. `decode.rs`: on the hardware device where there is one, else in software with dav1d for AV1. `vaapi.rs`: VA-API video processing, with which a VA-API encoder takes DMA-BUFs and scales their crop on the GPU |
| `none.rs` | The backend of a build without one; Android takes its encoder |

Encoders hold to low latency everywhere: no B-frames, no lookahead, a VBV of about two frames (VideoToolbox instead caps each second at the bitrate), and recovery by NVENC's intra refresh where it runs, else by an IDR on request. Decoders refuse pictures larger than the share announced. A hardware decoder that keeps failing for three seconds is swapped for software on Linux and Windows, and for AV1 and VP9 on Android; Android starts a new MediaCodec for H.264 and HEVC.

```sh
cargo test -p throcc-video --features ffmpeg     # Linux, Windows
cargo test -p throcc-video --features software   # dav1d and libvpx, from the system's
cargo test -p throcc-video                       # macOS, after packaging/codecs/build.sh and env.sh
```

Tests of an ffmpeg hardware encoder print `skipped:` where the hardware is missing. The VideoToolbox tests open Apple's software encoders, which CI's virtual Macs have, and fail rather than skip.
