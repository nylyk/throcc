# throcc-client-core

Everything a client does apart from drawing: connecting, keys, voice, screen share and the state the UI shows. Both the desktop client and `throcc-cli` build on it.

## Flow

The UI talks to a `ClientApi` from `client.rs`. It sends `UiCommand`s and reads a whole `State` after every change. `Client` is the real one: its tokio runtime runs the session task in `session.rs`, which signs in through `account.rs`, keeps `State` current, and reconnects into the room it was in. A sign-in pushes any other device of ours off the server, so the session signs in again unasked only while the link was up within the last five minutes by the wall clock, which keeps counting while the machine sleeps; past that it waits in `ConnectionStatus::AwaitingReconnect` for `UiCommand::Reconnect`. When the server says another device signed in as us, the session ends in `ConnectionStatus::SignedInElsewhere` and never signs in again by itself. `Client::connect` takes our profile as a watch, so a profile saved while it joins still reaches the server. `MockClient` answers locally with sample people and rooms, for screenshots and UI work.

Once signed in, a `Call` (`call.rs`) ties the `ControlLink` (`control.rs`) to the `MediaEngine` (`media/engine.rs`). The engine seals, fragments and sends our tracks, and receives, opens and reassembles everyone else's. The `KeyManager` (`keys.rs`) gives it a key for each sender and epoch.

Trust follows identity keys, not servers. The key manager wraps our sender secret to every room peer whose encryption key is validly signed by the identity key it presents, for this server and its user id, and whose presence the session has shown: the key manager of the session's call (`Call::start_shown`) hears where people are only from the session, which tells it of exactly who `State` shows and where, so nobody gets our key unseen, also while the session waits on a request. The session's `Trust` (`trust.rs`) notes every one of those identity keys, in the order they were trusted, also one the server replaced again before the session next looked at the room, and checks them against `VerifiedKeys` (`verified.rs`): the keys the user verified by safety number, kept once for the whole install, so someone verified on one server shows as verified on every server where their key appears. The app loads them once into a `VerifiedStore` and hands it to every session it starts, so the list is read and edited with no server connected; after the app changes it, `UiCommand::VerifiedChanged` has a running session show who is verified again. Only a key presented this connection counts: someone verified before shows as not verified, with no safety number, until they present that key in a room with us again, and then for the rest of the connection, even once they left the room. Everyone not verified is marked so but still hears us. Verifying names the key whose safety number the user compared, and is refused once that user presents another. Each verified key also remembers the server and user id pairs it was seen under; when a server shows a different, unverified key for one of them, `people.json` keeps a key-changed warning for that pair, across restarts and even once the old key is back, until the new key is verified, the old one unverified or the warning dismissed. Dismissing it while the verified key is back keeps watching the pair for the next change. While a warning stands, the newest key shown there is kept in memory and written with the next change to the file, so a server flipping keys can't make every room state rewrite it.

## Modules

| Module | Holds |
| --- | --- |
| `client.rs`, `session.rs`, `state.rs` | The UI's API, the session task, and the state it publishes |
| `blocked.rs` | The people blocked on this install, by the identity key the server names for them in their presence, so a block holds in every room and lobby of every server that shows the key. The app loads them once into a `BlockedStore` and hands it to every session; `UiCommand::Block` and `Unblock` change it from a room, and `UiCommand::BlockedChanged` has a running session follow a change made in settings. Only the drawing changes: a blocked person stays in `State`, under `BLOCKED_NAME` and without their picture, sounds or shares, so the key manager still wraps our key to them and nobody listens unseen. A block is only made or lifted from a room for a key the presence proves with the person's signed encryption key, so a server can only have it land on one of its own members; the key a presence names is enough to hide someone on that server; trust still comes only from the signed encryption key a peer presents in a shared room |
| `trust.rs` | Who is verified on one server: the identity keys presented this connection, checked against the verified ones, and the key-changed warnings |
| `account.rs`, `connection.rs`, `control.rs` | Sign-in and enrollment, the pinned QUIC connection, the control stream. Each enrollment takes a new encryption key and drops the epoch floors kept for the user id it gets, which may have stood for an earlier account of ours |
| `keystore.rs`, `known_servers.rs`, `verified.rs`, `floors.rs`, `playback.rs`, `server_look.rs` | What stays on this machine: our keys, pinned servers, the identity keys we verified, the newest epoch we took part in per room, how loud we play each person, saved under the identity key they present in a room with us and held in memory until they do, each server's name and picture as last seen. The identity key lives in the OS keychain (a 0600 `identity_key` file where there is none), the encryption key in `encryption_key`. `keystore/` holds the keychain per OS: on iOS an item that never leaves the device and is readable after the first unlock, on Android an `identity_key.wrapped` file sealed with an AES-GCM key that stays in the Android Keystore. A seed whose Keystore key is gone can never be read again and counts as a missing identity, so the user can start over; a seed that fails to open under its key is an error |
| `settings.rs`, `profile.rs`, `people.rs`, `servers.rs`, `json_file.rs`, `files.rs` | Where it stays: in the platform config directory, which a phone app sets with `keystore::set_app_dirs` before anything else, everything the user sets for the app in `settings.json` (our name and picture, which a session only gives to its server, the appearance, audio devices and voice settings, and whether to check for updates), everything per person by identity key in `people.json` (the verified keys with the server and user id pairs each was seen under, playback, and since version 2 the blocked people as they looked when blocked), and everything per server (epoch floors included) in `servers.json`. Every JSON change locks and re-reads the file first. `people.json` and `servers.json` take the change into what they read, so no writer undoes another; `settings.json` is replaced whole by the app's copy once it reads, so a rename the CLI makes while the app runs is undone by the app's next change. Files are written 0600 and replaced in one step. Each JSON file carries a `version`: an older one is migrated forward through its `json_file::Format::MIGRATIONS` as it loads, and a newer one is refused |
| `theme.rs` | What the desktop and the phone apps share of a theme: the preset themes as eight colours each, which theme the settings pick, the Custom theme's colours as hex, and whether a theme is a light one. Each frontend mixes its other colours from the eight itself |
| `avatars.rs` | Everyone's pictures, users' and servers', in the cache directory by hash. Each use marks a picture used; when a client connects, ones unused for 30 days go, then the least recently used until the cache is under 64 MiB |
| `keys.rs` | Sender secrets per epoch, wrapped to every peer with a validly signed encryption key; a new secret whenever those peers or their keys change, so a peer's routine encryption-key renewal starts a new secret too. Once we come back to a room, nothing at or before the newest epoch we took part in there (`floors.rs`, saved on each placement, every few seconds after, on disconnect and at exit, and kept across restarts) is accepted; within one stay, only the epoch just before the current one is, for a short grace |
| `call.rs` | A signed-in connection with its media engine |
| `media/engine.rs`, `fragment.rs`, `reorder.rs` | Sending and receiving media datagrams: fragments, the replay window, the reorder window |
| `media/voice.rs`, `audio.rs`, `devices.rs`, `jitter.rs` | The audio thread: mic processing and Opus, the mix, device rings, jitter buffers. It belongs to the app and runs without a server: settings, devices, the mic test, the level meter and cues need no session. A session plays and sends through a `CallAudio` handle; a newer handle takes the call audio over, commands from an older one are ignored, and dropping a handle ends its call's audio. Devices open at 48 kHz where they offer it; on macOS, where opening at another rate would change the device's rate for every app, at their current rate when 10 ms of it is a whole number of frames. Otherwise they open at their current rate under the same condition, or not at all. The audio thread resamples the rest. Devices are listed on a thread of their own, because on Windows cpal binds the listing thread to a single-threaded COM apartment. `devices.rs` has a backend per platform behind one `Devices`: cpal on desktop; on iOS one audio unit, the voice-processing one with the mic and plain remote I/O without; on Android AAudio streams with the voice-communication usage and input preset. A phone opens its devices with or without the mic, so someone who denies it still listens, and closes them outside a room. The capture chain leaves echo cancelling to the platform there |
| `media/cues.rs` | Join, leave, mute, deafen, connection, screen share and watching cues, synthesized once and mixed in by the audio thread |
| `media/share.rs`, `share_audio.rs` | Our running share: capture, encode, send. Its audio, and the audio-led sync of shares we watch |
| `media/capture/` | Screen and system-audio capture per OS: ScreenCaptureKit, Windows Graphics Capture with process loopback, the portal with PipeWire. The portal keeps nothing of what was picked, so every share asks again |
| `media/video/` | Encode and decode through ffmpeg, hardware first, and the NV12 frames between them, with their conversions from 4-byte RGB pixels and to BGRA. On macOS, our own share's preview and VideoToolbox-decoded pictures reach the UI as the pixel buffers they are in, uncopied |

Video needs the `ffmpeg` feature. Without it the client does voice only. Audio and capture callbacks never block, allocate, lock or panic; they reach tokio only through bounded rings that drop when full.

## Manual hardware tests

These tests are `#[ignore]`d because they need a display, a desktop session or audio hardware, and no CI job runs them. Run one by name on a machine that has what its `ignore` reason names:

```sh
cargo test -p throcc-client-core --features ffmpeg --lib -- --ignored <name>
```

| OS | Test | Needs |
| --- | --- | --- |
| Linux | `pipewire_source_delivers_converted_frames` | A PipeWire daemon and a session manager |
| Linux | `desktop_audio_has_other_apps_but_not_ours` | The same, an audio sink and `pw-play` |
| Linux | `portal_share_delivers_frames_and_asks_every_time` | A desktop session with xdg-desktop-portal, and someone to pick a screen |
| macOS | `main_display_delivers_frames`, `share_audio_arrives_in_order_with_sound` | A display, the screen recording permission, and speakers for the second |
| macOS | `sending_1440p60_takes_under_one_core` | The same, with moving content on the display |
| Windows | `primary_monitor_delivers_frames`, `share_audio_arrives_in_order_with_sound` | A display, a GPU, and speakers for the second |

The VA-API tests (`gpu_input`) and the VideoToolbox ones run in the normal suite and print `skipped:` where the hardware is missing.
