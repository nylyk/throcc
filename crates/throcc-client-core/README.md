# throcc-client-core

Everything a client does apart from drawing: connecting, keys, voice, screen share and the state the UI shows. Both the desktop client and `throcc-cli` build on it.

## Flow

The UI talks to a `ClientApi` from `client.rs`. It sends `UiCommand`s and reads a whole `State` after every change. `Client` is the real one. `Client::connect` gets on through an `Entry`: a sign-in, which gives up once its `cancelled` future resolves, or an enrollment with an invite, which runs to its end because the server may make the account before answering. Every client starts its sign-ins through `SignIns`, where starting one gives up every older one and only the newest one's result counts. Its tokio runtime runs the session task in `session.rs`, which signs in through `account.rs`, keeps `State` current, and reconnects into the room it was in. A sign-in pushes any other device of ours off the server, so the session signs in again unasked only while the link was up within the last five minutes by the wall clock, which keeps counting while the machine sleeps; past that it waits in `ConnectionStatus::AwaitingReconnect` for `UiCommand::Reconnect`. When the server says another device signed in as us, the session ends in `ConnectionStatus::SignedInElsewhere` and never signs in again by itself. Every sign-in gives the server our profile from `settings.json`, signed for the user id the server names, so a server never holds a profile of ours without our signature; a profile saved during the join reaches the server as an ordinary change once the app has the session. `MockClient` answers locally with sample people and rooms, for screenshots and UI work.

Once signed in, a `Call` (`call.rs`) ties the `ControlLink` (`control.rs`) to the `MediaEngine` (`media/engine.rs`). The engine seals, fragments and sends our tracks, and receives, opens and reassembles everyone else's. The `KeyManager` (`keys.rs`) gives it a key for each sender and epoch.

Trust follows identity keys, not servers. The key manager wraps our sender secret to every room peer whose encryption key is validly signed by the identity key it presents, for this server and its user id, and whose presence the session has shown: the key manager of the session's call (`Call::start_shown`) hears where people are only from the session, which tells it of exactly who `State` shows and where, so nobody gets our key unseen, also while the session waits on a request. The session's `Trust` (`trust.rs`) notes every one of those identity keys, in the order they were trusted, also one the server replaced again before the session next looked at the room, and the identity key of every presence that places someone outside our room and whose signature over its name and picture verifies for this server and its user id, and checks them against `VerifiedKeys` (`verified.rs`): the keys the user verified by safety number, kept once for the whole install, so someone verified on one server shows as verified on every server where their key appears. The app loads them once into a `VerifiedStore` and hands it to every session it starts, so the list is read and edited with no server connected; after the app changes it, `UiCommand::VerifiedChanged` has a running session show who is verified again. Only a key presented this connection counts: someone verified before shows as not verified, with no safety number, until they present that key again, as a room peer or by a signed presence that places them outside our room, and then until their presence ends or they stop presenting it: a presence that fails its signature, or one that shows them in our room without them being a trusted peer there. A signed presence lets the user compare safety numbers before sharing a room. A server replaying an old presence can only show a key that person once held, and our sender secret still goes only to room peers' freshly signed encryption keys; a room peer must present the same key as its presence for a block to be made or lifted. Everyone not verified is marked so but still hears us. Verifying names the key whose safety number the user compared, and is refused once that user presents another. Each verified key also remembers the server and user id pairs it was seen under; when a server shows a different, unverified key for one of them, `people.json` keeps a key-changed warning for that pair, across restarts and even once the old key is back, until the new key is verified, the old one unverified or the warning dismissed. Dismissing it while the verified key is back keeps watching the pair for the next change. While a warning stands, the newest key shown there is kept in memory and written with the next change to the file, so a server flipping keys can't make every room state rewrite it.

## Modules

| Module | Holds |
| --- | --- |
| `client.rs`, `session.rs`, `state.rs` | The UI's API, the session task, and the state it publishes, with what every client derives from it the same way: trust per person and the name a key was verified under, what picking a room does, the room we are live in, the connection notice, the volume slider curve. Account and profile checks and their wording sit in `account.rs` (why a sign-in failed) and `profile.rs` (names, passwords, pictures) |
| `blocked.rs` | The people blocked on this install, by the identity key the server names for them in their presence, so a block holds in every room and lobby of every server that shows the key. The app loads them once into a `BlockedStore` and hands it to every session; `UiCommand::Block` and `Unblock` change it from a room, and `UiCommand::BlockedChanged` has a running session follow a change made in settings. Only the drawing changes: a blocked person stays in `State`, under `BLOCKED_NAME` and without their picture, sounds or shares, so the key manager still wraps our key to them and nobody listens unseen. A block is only made or lifted from a room for a key the presence proves with the person's signature over their name and picture, so a block lands only on the member who chose the name and picture it was made on; the key a presence names is enough to hide someone on that server |
| `trust.rs` | Who is verified on one server: the identity keys presented this connection by signed presences and room peers, checked against the verified ones, and the key-changed warnings |
| `account.rs`, `connection.rs`, `control.rs` | Sign-in and enrollment, both ending with our profile signed for the user id the server names, the pinned QUIC connection, the control stream. Every sign-in also signs the address it reached the server at. A server the identity joined from another device is added by its address alone: before we sign anything for it, it shows that address signed by us for its key and our user id, and is pinned then. One that can't, or doesn't know us, needs an invite, and a key already pinned under another address is refused. Each enrollment takes a new encryption key and drops the epoch floors kept for the user id it gets, which may have stood for an earlier account of ours |
| `keystore.rs`, `known_servers.rs`, `verified.rs`, `floors.rs`, `playback.rs`, `server_look.rs` | What stays on this machine: our keys, pinned servers, the identity keys we verified, the newest epoch we took part in per room, how loud we play each person, saved under the identity key they present and held in memory until they do, each server's name and picture as last seen. The identity key lives in the OS keychain (a 0600 `identity_key` file where there is none), the encryption key in `encryption_key`. `keystore/` holds the keychain per OS: on iOS an item that never leaves the device and is readable after the first unlock, on Android an `identity_key.wrapped` file sealed with an AES-GCM key that stays in the Android Keystore. A seed whose Keystore key is gone can never be read again and counts as a missing identity, so the user can start over; a seed that fails to open under its key is an error |
| `settings.rs`, `profile.rs`, `people.rs`, `servers.rs`, `json_file.rs`, `files.rs` | Where it stays: in the platform config directory, which a phone app sets with `keystore::set_app_dirs` before anything else, everything the user sets for the app in `settings.json` (our name and picture, which a session only gives to its server, the appearance, audio devices and voice settings, and whether to check for updates), everything per person by identity key in `people.json` (the verified keys with the server and user id pairs each was seen under and, since version 3, the picture they had when verified, playback, and since version 2 the blocked people as they looked when blocked), and everything per server (epoch floors included) in `servers.json`. Every JSON change locks and re-reads the file first. `people.json` and `servers.json` take the change into what they read, so no writer undoes another; `settings.json` is replaced whole by the app's copy once it reads, so a rename the CLI makes while the app runs is undone by the app's next change. Files are written 0600 and replaced in one step. Each JSON file carries a `version`: an older one is migrated forward through its `json_file::Format::MIGRATIONS` as it loads, and a newer one is refused |
| `theme.rs` | What the desktop and the phone apps share of a theme: the preset themes as eight colours each, which theme the settings pick (picking a preset keeps the Custom theme's colours as they stand), the Custom theme's colours as hex, whether a theme is a light one, and `Colors`: the colours every client mixes from the eight in Oklab, with muted, accent and status colours pushed toward the text colour until they read at 4.5:1 on every surface |
| `install.rs` | What the install keeps, as every client loads and lists it: the settings, verified and blocked stores, each read so a damaged file starts the app without it and says why, the known servers with their last look, the sample servers, and the verified and blocked lists as shown, with a blocked person's name hidden |
| `transfer.rs`, `fountain.rs` | Moving an identity to another device. `transfer` gathers the identity key, our profile, the servers with their names and pictures, and the verified and blocked people with the standing key-changed warnings, and seals them with `throcc_crypto::transfer` under a new code, stamped with when. An import opens an export no older than an hour, makes its identity the install's with a new encryption key while no server knows the install's own, merges the people into those kept, and pins the servers last, so one cut short can run again. `fountain` cuts the sealed export into endless fountain-coded frames in base 45 for QR alphanumeric mode, the first ones each one block and later ones the XOR of a few, and collects scanned frames in any order with a progress estimate. A file holds the sealed export as it is |
| `picture.rs` | Profile pictures: the one the user picks made into a 128 px JPEG square, transparency on white, and every picture read only as JPEG of at most 512 px, checked before their pixels are allocated. The phones check a picture's header with `showable` before their own decoders see it |
| `safety.rs` | `SafetyCheck`, a safety-number comparison as a profile shows it: the number stays on the key being compared, a key presented while it is open shows its new number with a warning, and marking or dismissing waits until the user compares again. Only the key whose number was on screen is sent |
| `avatars.rs` | Everyone's pictures, users' and servers', in the cache directory by hash. Each use marks a picture used; when a client connects, ones unused for 30 days go, then the least recently used until the cache is under 64 MiB |
| `keys.rs` | Sender secrets per epoch, wrapped to every peer with a validly signed encryption key; a new secret whenever those peers or their keys change, so a peer's routine encryption-key renewal starts a new secret too. Once we come back to a room, nothing at or before the newest epoch we took part in there (`floors.rs`, saved on each placement, every few seconds after, on disconnect and at exit, and kept across restarts) is accepted; within one stay, only the epoch just before the current one is, for a short grace |
| `call.rs` | A signed-in connection with its media engine |
| `media/engine.rs`, `fragment.rs`, `reorder.rs` | Sending and receiving media datagrams: fragments, the replay window, the reorder window |
| `media/voice.rs`, `audio.rs`, `devices.rs`, `jitter.rs` | The audio thread: mic processing and Opus, the mix, device rings, jitter buffers. It belongs to the app and runs without a server: settings, devices, the mic test, the level meter and cues need no session. A session plays and sends through a `CallAudio` handle; a newer handle takes the call audio over, commands from an older one are ignored, and dropping a handle ends its call's audio. Devices open at 48 kHz where they offer it; on macOS, where opening at another rate would change the device's rate for every app, at their current rate when 10 ms of it is a whole number of frames. Otherwise they open at their current rate under the same condition, or not at all. The audio thread resamples the rest. Devices are listed on a thread of their own, because on Windows cpal binds the listing thread to a single-threaded COM apartment. `devices.rs` has a backend per platform behind one `Devices`: cpal on desktop; on iOS one remote I/O audio unit; on Android AAudio media streams. Both phones play as media, whose volume goes down to silence. A phone opens its devices with or without the mic, so someone who denies it still listens, and closes them outside a room. The capture chain cancels echo itself on every platform |
| `media/cues.rs` | Join, leave, mute, deafen, connection, screen share and watching cues, synthesized once and mixed in by the audio thread |
| `media/share.rs`, `share_audio.rs` | Our running share: capture, encode, send, with the last picture sent again every half second while the screen stands still. Decoding the shares we watch on a thread each, which drops a backlog it can't keep up with and goes on from a keyframe. Their audio, and the audio-led sync of shares we watch |
| `media/capture/` | Screen and system-audio capture per OS: ScreenCaptureKit, Windows Graphics Capture with process loopback, the portal with PipeWire. The portal keeps nothing of what was picked, so every share asks again. `clock.rs` stamps a capture's video and audio from one zero, and `limiter.rs` holds its frames to the share's rate |
| `media/video.rs` | The newest picture of each share as the UI gets it, and when the UI last drew our own preview. The codecs, frames and the phones' `Output`, where a decoder shows a share in the app's `View` itself, are in `throcc-video`; on macOS, our own share's preview and decoded pictures reach the UI as the pixel buffers they are in, uncopied |

Video needs a backend in `throcc-video`: VideoToolbox with dav1d and libvpx on macOS and iOS, MediaCodec with dav1d and libvpx on Android, or on Linux and Windows its `ffmpeg` feature, which this crate's `ffmpeg` feature turns on. The phones only watch shares. Without a backend the client does voice only. Audio and capture callbacks never block, allocate, lock or panic; they reach tokio only through bounded rings that drop when full.

## Manual hardware tests

These tests are `#[ignore]`d because they need a display, a desktop session or audio hardware, and no CI job runs them. Run one by name on a machine that has what its `ignore` reason names:

```sh
cargo test -p throcc-client-core --features ffmpeg --lib -- --ignored <name>
```

| OS | Test | Needs |
| --- | --- | --- |
| Linux | `pipewire_source_delivers_converted_frames` | A PipeWire daemon and a session manager |
| Linux | `desktop_audio_has_other_apps_but_not_ours` | The same, an audio sink and `pw-play` |
| Linux | `portal_share_delivers_frames_and_asks_every_time` | A desktop session with xdg-desktop-portal, and someone to pick a screen |
| macOS | `main_display_delivers_frames`, `share_audio_arrives_in_order_with_sound` | A display, the screen recording permission, and speakers for the second |
| macOS | `sending_1440p60_takes_under_one_core` | The same, with moving content on the display |
| Windows | `primary_monitor_delivers_frames`, `share_audio_arrives_in_order_with_sound` | A display, a GPU, and speakers for the second |

The hardware video tests live in `throcc-video` and print `skipped:` where the hardware is missing.
